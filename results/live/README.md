## v1 분석

매 수 기록된 페이지 상태를 엔진에 옮겨 그 수를 그대로 두고, 다음 수 시점의 페이지 상태와 비교했습니다.

- 위치 오차: 중앙값 2.6px, 상위 10% 30px 이상. 258수 중 11수는 합성 결과(과일 구성·점수)까지 달랐습니다.
- 원인: 물리를 다시 켠 뒤 클릭해서, 클릭이 반영되기 전에 페이지가 여러 프레임(대부분 6프레임 이상)을 먼저 굴렸습니다. 에이전트가 계산한 판과 실제로 떨어뜨린 판이 달랐습니다.
- 수정: 물리를 멈춘 상태에서 클릭하고, 페이지가 과일을 받은 걸 확인한 뒤 다시 켭니다.

마지막 수는 직전 수의 연쇄 합성으로 멜론이 경계선 근처(위쪽 끝 y≈22)에 생긴 상태였습니다. 그 판에서는 어디에 떨어뜨려도 곧바로 게임오버였습니다(61곳 모두). 직전 수의 판에서도 61곳 중 14곳은 4초 안에 게임오버로 이어지는 위험한 판이었습니다. 몬테카를로는 2초(120프레임)만 내다보고 채점 공식에 "위쪽이 위험하다"는 항목이 없어서, 이런 지연된 위험을 잘 피하지 못합니다.

## v2 분석

- 점수 3592점으로 엔진(3593점)과 거의 같지만 우연입니다. 둘의 판은 2수째부터 낙하 위치가 소수점 아래에서 갈라졌습니다. 점수대가 엔진 수준으로 돌아온 건 v1의 클릭 타이밍 버그가 원인이었다는 뜻입니다.
- 기록의 물리 시각(`t`)으로 수 사이 프레임을 정확히 맞춰 비교하면 위치 오차 중앙값 0.9px, 361수 중 8수만 합성 결과가 달랐습니다.
- 남은 문제: 수 사이에 물리가 엔진(72프레임)보다 훨씬 오래(중앙값 약 350프레임) 돌았습니다. 물리를 다시 켜는 호출이 물리 세계 전체를 반환해서, Playwright가 그걸 직렬화하는 동안 판이 계속 굴렀고 과일이 많아질수록 길어졌습니다. 판이 더 오래 가라앉은 상태에서 다음 수를 둔 셈이라, 실제 사이트 판이 엔진 판보다 조금 쉬운 조건이었습니다.
- 수정(v3): 호출이 아무것도 반환하지 않게 하고, 다음 과일을 놓을 수 있게 되는 첫 프레임에 페이지 안에서 바로 물리를 멈추도록 했습니다.

## v3 분석

- 이번 실행은 페이지가 60fps로 돌아 60Hz 기준으로 계산했습니다(v1, v2는 120Hz). 엔진의 같은 조건(시드 0, 60Hz) 점수는 4022점(404수)입니다.
- 수 사이 물리 프레임이 37프레임으로 일정했습니다(엔진 36프레임 + 멈추기 전 1프레임). v2에서 58~629프레임으로 들쭉날쭉하던 문제가 해결됐습니다.
- 수마다 예측 위치 오차는 중앙값 2.6px, 410수 중 13수에서 합성 결과가 달랐습니다. 낙하 x를 조금씩 옮겨봐도 오차가 줄지 않아서, 클릭 위치 문제는 아닙니다. 판을 엔진에 옮길 때 접촉 정보가 빠지는 영향으로 봅니다.
