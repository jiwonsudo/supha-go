# 엔진

## 원본 분석

playsuikagame.com의 게임 스크립트를 브라우저에서 직접 확인했습니다.

- 엔진: Phaser 3.70.0, 물리는 그 안에 들어 있는 Matter.js 0.19.0
- 스크립트는 난독화돼 있고 다른 도메인에선 동작을 막는 코드가 있습니다. 원본 코드는 가져오지 않고, 확인한 동작을 보고 규칙을 새로 작성했습니다.
- 물리 엔진은 Phaser 패키지 안의 Matter.js 소스를 그대로 불러 씁니다 (`phaser@3.70.0` 고정).

## 물리값과 규칙

| 항목 | 값 |
|---|---|
| 중력 | y 1.5, scale 0.001 |
| 솔버 | position 6, velocity 4, restingThresh 4, restingThreshTangent 6 |
| 과일 | 원형(26각형), friction 1, frictionStatic 0.5, frictionAir 0.01, restitution 0, 0.75배 스케일 |
| 과일 반지름 | 18.375, 23.625, 33, 36, 45.75, 58.5, 68.25, 83.625, 94.125, 115.875, 135 |
| 통 | 캔버스 654×724, 벽 x 55~599, 바닥 y 708 |
| 생성 | 첫 과일 체리 고정, 이후 작은 5종 균등 랜덤, 다음 과일 공개 |
| 낙하 | y 80, 다음 낙하까지 600ms |
| 합성 | 같은 과일끼리 충돌하면 둘 다 제거, id가 작은 쪽 위치에 다음 단계 생성. 수박끼리는 둘 다 사라짐 |
| 점수 | 1, 3, 6, 10, 15, 21, 28, 36, 45, 55, 66 (합쳐진 과일 단계별) |
| 게임오버 | 다른 과일끼리 충돌할 때 한쪽의 (y - centerOffset.y/2) < 70 |

**솔버 값 2개**는 라이브러리 기본값(2, 약 2.45)과 다릅니다. 이걸 맞추기 전에는 과일이 닿자마자 원본과 결과가 갈렸습니다.

**화면 주사율**: 원본은 화면 주사율과 상관없이 물리를 한 프레임에 1/60초씩 진행하는데, 600ms 대기는 실제 시간 기준입니다. 그래서 60Hz 화면에선 대기 중 36프레임, 120Hz 화면에선 72프레임이 흐르고, 같은 수를 둬도 다른 게임이 됩니다. 엔진은 `displayHz` 옵션으로 둘 다 지원하고, 벤치마크 기본값은 60Hz입니다.

## 주요 기능

```js
const { SuikaGame } = require('./engine/src/suika');
const g = new SuikaGame({ seed: 1, displayHz: 60 });
g.turn(300);          // 현재 과일을 x=300에 떨어뜨리고 다음 낙하 가능 시점까지 진행
const b = g.clone();  // 탐색용 분기 (같은 수를 두면 같은 결과)
```

- `stepFrame()`: 물리 1프레임 진행, 낙하 대기 시간 차감
- `drop(x)` / `turn(x)`: 떨어뜨리기 / 떨어뜨리고 다음 수 시점까지 진행
- `clone()`: 물리 엔진 내부 상태 전체(과일, 접촉 캐시, 충돌 순서, 난수 상태)를 통째로 복사. 탐색의 기반입니다.
- `fromState(state)`: 외부에서 읽은 과일 목록으로 게임을 재구성. 실제 사이트 판을 엔진에 옮길 때 씁니다. 접촉 캐시는 복사되지 않아서 처음 몇 프레임은 조금 다를 수 있습니다.
- 난수: 시드를 넣는 mulberry32. 같은 시드면 같은 과일 순서입니다.

## 검증

| 확인 | 결과 |
|---|---|
| 원본에서 녹화한 24수와 비교 (`compare_ref.js`) | 점수와 과일 구성은 끝까지 같음. 좌표는 약 9수까지 소수점 12자리까지 같음 |
| clone 결정성 | 복사본에 같은 수 80개를 두면 상태가 완전히 같음 |
| 실제 페이지 판을 옮겨 4초 진행 | 위치 오차 최대 0.1px, 합성과 점수 같음 |
| 환경별 상태 해시 (`golden.js`) | 맥, 작업공간, 클라우드 모두 `b25a5754044cb428` |

**9수 뒤 좌표가 갈라지는 이유**: 브라우저(Chrome 152)와 Node의 `Math.sin`/`Math.cos`가 마지막 자리에서 다른 값을 냅니다. 같은 입력으로 두 환경에서 해시를 비교해 확인했습니다. 물리가 혼돈계라 이 미세한 차이가 몇 수 뒤에 커집니다. 원본도 브라우저마다 같은 이유로 조금씩 다르게 돌아가서, "원본과 비트 단위로 같다"는 기준은 원본 자체에도 성립하지 않습니다.

## 속도

- 랜덤 플레이 기준 코어당 초당 약 58턴 (작업공간 서버)
- 몬테카를로 1수는 한 수에 50곳 × 120프레임을 굴려서 약 1.5~2초
- 프로파일링 결과 `Collision.collides`가 68%, 그중 91%가 실제 접촉이라 결과를 유지하는 최적화 여지가 거의 없었습니다. 외접원으로 미리 거르는 최적화를 시도했지만 속도 변화가 없어 되돌렸습니다.
