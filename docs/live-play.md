# 실제 사이트에서 플레이

`python/suphago/live.py`가 Playwright로 Chromium을 띄워 playsuikagame.com에서 에이전트가 직접 둡니다.

## 동작 순서

1. 사이트를 엽니다. 팝업은 사람이 직접 닫고 터미널에서 Enter를 누릅니다.
2. `--seed`를 주면 페이지의 과일 뽑기 함수(`randomFruit`)를 엔진과 같은 난수로 바꿔치기해서, 엔진의 같은 시드와 같은 순서로 과일이 나오게 합니다. 시작할 때 첫 과일이 엔진과 같은지 확인합니다.
3. 화면 주사율을 1초 동안 재서 60Hz / 120Hz를 정합니다.
4. 페이지 안에 훅을 심어, 다음 과일을 놓을 수 있게 되는 첫 프레임에 물리를 멈춥니다.
5. 과일 전부(종류, 위치, 속도, 회전)와 현재/다음 과일, 점수를 읽습니다.
6. 그 판을 `fromState`로 엔진에 옮기고 에이전트가 x를 고릅니다.
7. 멈춘 상태에서 캔버스의 그 위치를 실제 마우스로 클릭합니다.
8. 페이지가 과일을 받은 걸 확인한 뒤 물리를 다시 켭니다.

`--no-pause`를 주면 멈추지 않고 실시간으로 둡니다. 생각하는 동안 판이 움직여서 계획이 조금씩 어긋납니다.

게임이 끝나면 원본 페이지가 점수를 공개 리더보드에 올립니다. 매 수 물리를 멈추고 두기 때문에 사람의 일반 플레이와 조건이 다릅니다.

## 찾은 버그와 수정

| 버전 | 점수 (시드 0) | 문제 | 수정 |
|---|---|---|---|
| v1 | 2418 (120Hz) | 물리를 다시 켠 뒤 클릭해서, 클릭이 반영되기 전에 대부분 6프레임 넘게 먼저 굴렀음. 계획한 판과 떨어뜨린 판이 달랐음 | 멈춘 상태에서 클릭하고, 과일이 들어간 걸 확인한 뒤 재개 |
| v2 | 3592 (120Hz) | 수 사이 물리가 72프레임이 아니라 중앙값 약 350프레임 돌았음. 물리를 켜는 명령이 물리 세계 전체를 반환해서, Playwright가 그걸 직렬화하는 동안 판이 계속 굴렀고 과일이 많을수록 길어졌음 | 명령이 아무것도 반환하지 않게 하고, 페이지 안 훅으로 첫 프레임에 바로 멈춤 |
| v3 | 4107 (60Hz) | 수 사이 37프레임으로 일정 (엔진 36 + 멈추기 전 1) | |

**분석 방법**: 매 수 기록된 페이지 판을 엔진에 옮기고 같은 수를 둔 뒤, 다음 수 시점의 페이지 판과 과일 위치를 비교했습니다. v2부터는 기록에 물리 시각(`t`)을 남겨서 수 사이 프레임 수를 정확히 맞춰 비교합니다. v1의 원인은 "클릭 전에 몇 프레임이 지났다고 가정하면 가장 잘 맞는가"를 찾아 확인했습니다.

v2의 3592점이 엔진(3593점)과 거의 같은 건 우연입니다. 두 판은 2수째 낙하 위치부터 소수점 아래에서 갈라졌습니다.

## 남은 차이

v3 기준으로 수마다 예측 위치 오차는 중앙값 2.6px, 410수 중 13수에서 합성 결과가 달랐습니다. 낙하 x를 조금씩 옮겨봐도 오차가 줄지 않아서 클릭 위치 문제는 아닙니다. 판을 엔진에 옮길 때 접촉 캐시가 빠지는 영향으로 봅니다. 에이전트는 매 수 실제 판을 다시 읽기 때문에 오차가 쌓이지 않습니다.

## 게임오버 사례 (v1)

마지막 수는 직전 수의 연쇄 합성으로 멜론이 경계선 근처(위쪽 끝 y≈22)에 생긴 상태였고, 어디에 떨어뜨려도(61곳 모두) 바로 게임오버였습니다. 직전 판에서도 61곳 중 14곳은 4초 안에 게임오버로 이어졌습니다. 몬테카를로는 2초만 내다보고 채점 공식에 "위쪽이 위험하다"는 항목이 없어서 이런 지연된 위험을 피하지 못합니다. 가치망의 게임오버 출력이 노리는 부분입니다.

기록 파일과 분석은 [results/live/](../results/live/)에 있습니다.
